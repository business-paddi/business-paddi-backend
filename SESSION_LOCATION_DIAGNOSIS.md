# Session location diagnosis

Investigated: 2026-10-07. Production is reported to use `TRUST_PROXY=1`.

## Findings

The backend does not produce an "Unknown location" string. It returns nullable `city`, `region`, and `country` fields, so that label is generated by the consuming UI. No frontend source or production request headers were available for this investigation.

The location-to-session wiring is intact. All successful password, Google, and email-code login paths pass the current request context to `SessionService.createLoginSession`. That method stores the resolved IP and location fields on `UserSession`. Session listing selects and returns those same fields directly.

There is a confirmed limitation: session location is a login-time snapshot. Refresh rotation changes token linkage and last-seen timestamps but does not update the saved IP or location. Existing sessions with null location remain null after changing proxy settings or updating GeoIP data. Test a genuinely new login session when verifying a fix.

`TRUST_PROXY=1` is a hop count, not a guarantee that the visitor IP is selected. Express trusts the immediate socket peer and selects the rightmost X-Forwarded-For entry. With an additional internal proxy, this can select a private address. `LocationService` deliberately returns null location for non-public addresses. A frontend server making the backend request without preserving the visitor address can also cause the backend to see the frontend server's IP.

## Trace

1. `src/main.ts`: reads `TRUST_PROXY`, converts numeric strings to numbers, and sets Express trust before listening. The string `1` is parsed correctly.
2. `src/common/utils/request-metadata.ts`: reads Express `request.ip`, falling back to the socket only when absent. Does not directly trust raw forwarding headers.
3. `src/common/utils/ip-address.ts`: normalizes IPv4-mapped dotted IPv6 and zones; rejects invalid IP strings. Private, loopback, carrier-grade NAT, and reserved ranges are excluded from GeoIP lookup.
4. `src/location/location.service.ts`: opens `MAXMIND_DB_PATH` at startup; missing/unreadable database throws and prevents startup. Looks up public addresses and maps English country, subdivision, and city names. Invalid/non-public addresses and absent GeoIP records return null fields.
5. `src/auth/auth.controller.ts`: obtains context for login, Google callback, verification, and refresh requests.
6. `src/auth/auth.service.ts`: password and Google login create a session, or defer creation until email-code verification. Verification uses the verification request's context.
7. `src/session/session.service.ts`: creates a UserSession containing IP, city, region, and country; creates the AuthSession token chain; persists the same context in the login audit event.
8. Refresh rotation audits its current context, but only updates the UserSession token pointer and lastSeenAt. The access guard validates authentication but does not update location either.
9. `GET /api/sessions`: returns stored city/region/country as top-level session fields. It does not resolve location again or nest those fields inside a `location` object.

## Reproduced locally

The actual installed Express IP resolver and the local GeoLite2-City database produced:

| Socket peer | X-Forwarded-For | Trust | Selected IP | Lookup |
| --- | --- | --- | --- | --- |
| 10.0.0.10 | 197.210.29.1 | 1 | 197.210.29.1 | Lagos, Lagos, Nigeria |
| 10.0.0.10 | 197.210.29.1, 10.0.0.5 | 1 | 10.0.0.5 | No location |
| 10.0.0.10 | 197.210.29.1:54321 | 1 | 197.210.29.1:54321 | Invalid IP; no location |

The local database identifies itself as GeoLite2-City, supports IPv6, and has build timestamp 2026-10-02. This confirms local lookup works; it does not establish which database or headers production uses. All 17 existing IP utility tests passed.

## Determine the production cause

Inspect a fresh login's `GET /api/sessions` response and matching `authentication.login.succeeded` audit event. Compare its saved `ipAddress`, `city`, `region`, and `country`:

- Private/loopback/CGNAT IP: lookup was intentionally skipped. Investigate the forwarding chain and hop trust configuration.
- Null IP: selected address failed normalization; inspect for IP:port or bracketed formatting.
- Public IP with null city but populated country/region: GeoIP has partial coverage. The frontend should display the available fields rather than require a city.
- Public IP with all location fields null: inspect the production database type/version and lookup that exact IP. It may have no record, or the deployment may be using a different database.
- API location fields populated but UI says unknown: check that the frontend reads top-level fields and its fallback logic.
- Login session fields null, but later refresh audit fields populated: original context was unknown; refresh does not repair it.

To reproduce the production header selection and database lookup on the deployment, run from the application's working directory:

```sh
node scripts/diagnose-location.cjs 'CLIENT_IP, INTERMEDIATE_PROXY_IP' 'SOCKET_PEER_IP'
```

Substitute the actual X-Forwarded-For and socket peer observed at the backend. The script uses configured TRUST_PROXY and MAXMIND_DB_PATH, prints database metadata and selection results, and performs no database writes. Without arguments it runs the synthetic cases above. Its output contains the IPs supplied, so handle it as request diagnostics.

Do not blindly raise trust or select the leftmost raw header. Use the verified forwarding topology: one sanitized forwarding hop can use 1; additional hops require matching trust settings or explicit trusted proxy subnets, and a frontend proxy must preserve the visitor IP through a trusted chain. Header formatting is a separate issue from hop count.

Reference: https://expressjs.com/en/guide/behind-proxies/

## Render follow-up

The backend is hosted on a Render web service. Render documents Cloudflare and load balancers in its public request path, but does not guarantee a fixed hop count in the referenced guidance: https://render.com/articles/how-render-handles-ddos-attacks

Added authenticated `GET /api/sessions/location-diagnostics` with `Cache-Control: no-store`. It returns the configured trustProxy, socketIp, raw forwardedFor, normalized resolvedIp, and current location lookup. It reads only the calling request, does not access or change saved sessions, and uses the controller's AccessTokenGuard.

After deploying this code, call that endpoint from the signed-in browser using the same API path as login. Compare resolvedIp with the visitor's public IP and inspect forwardedFor from right to left. If the header is `CLIENT, PROXY_A, PROXY_B` and the socket is another trusted Render proxy, the appropriate hop count for that observed path is 3; if it is `CLIENT, PROXY_A`, it is 2. Verify every public path before adopting a fixed count. Do not infer 3 solely from the host name. Existing main.ts already parses numeric TRUST_PROXY values, so a verified hop change needs only a Render environment update and redeploy.

If resolvedIp is correct but current location is empty, use the deployment lookup script with that IP to verify production GeoLite2 coverage. If current location is populated while a saved session is empty, log out and log in to create a fresh snapshot. If the session response is populated but the UI is unknown, fix the frontend to consume top-level city/region/country and use available country/region as fallback.
