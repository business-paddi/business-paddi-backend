# Remita payroll feasibility and local proof of concept

Research date: 2026-10-31. Source: [official Remita API documentation](https://api.remita.net/), sections Authentication–First Generation APIs, Invoice Generation, Request Fields, Response Codes, and Payment Notification. The documentation is a single page. Direct retrieval through the browser tool returned 402; its search-indexed official content supplied the schemas below. No unofficial credentials, endpoints or third-party SDK claims were used.

## Confirmed first-generation invoice contract

Sandbox invoice root: `https://demo.remita.net/remita/exapp/api/v1/send/api/echannelsvc`. The documentation also uses `remitademo.net` in some examples; this implementation pins the former and never follows redirects. No production host is supported.

- POST `merchant/api/paymentinit`: JSON fields `serviceTypeId`, `amount`, `orderId`, `payerName`, `payerEmail`, `payerPhone`, `description`, and `lineItems`. Each split has `lineItemsId`, `beneficiaryName`, `beneficiaryAccount`, `bankCode`, `beneficiaryAmount`, `deductFeeFrom` (`"0"` or `"1"`). `amount` and beneficiary amounts are decimal naira strings. Signature: SHA-512 of merchantId + serviceTypeId + orderId + the exact amount string sent + apiKey. Header: `Authorization: remitaConsumerKey=<merchantId>,remitaConsumerToken=<hexDigest>`; `Content-Type: application/json`. Successful generation uses `statuscode: "025"`, `RRR`, `status`. JSONP-wrapped examples also exist; parse only the literal JSON wrapper, never evaluate JavaScript.
- GET `<merchantId>/<RRR>/<hash>/status.reg`, hash SHA-512(RRR + apiKey + merchantId). GET `<merchantId>/<orderId>/<hash>/orderstatus.reg` reconciles by merchant reference, using SHA-512(orderId + apiKey + merchantId). Response fields shown are `amount` (number), `RRR`, `orderId`, `message`, `transactiontime`, optional `paymentDate`, `status` (code). `00`/`01` indicate paid collection; `021` pending; `02` failed. Other codes remain unknown/reviewable rather than guessed.
- POST `v2/api/deactivate.json`: `{ rrr, merchantId, hash }`, hash SHA-512(rrr + apiKey + merchantId). Documented success is `statuscode: "00"`, possibly JSONP-wrapped. Only unpaid invoices qualify. API availability is not a guarantee of merchant entitlement or race-free cancellation; local cancellation remains unknown after transport failure.
- Notifications are JSON arrays, with `rrr`, `orderId`/`orderRef`, `amount`, `transactiondate`, `type` and other payer/transaction fields. The documented acknowledgement is plain text `Ok`. No invoice-webhook signature scheme is supplied in that section. Treat the entire callback as untrusted: deduplicate a fingerprint, enqueue reconciliation, and obtain status independently. Never use callback amount/status as verified evidence.

The first-generation response table lists errors for unprofiled beneficiaries and accounts not linked to a merchant. This is evidence that split beneficiary eligibility cannot be assumed. The split example's displayed amounts are internally inconsistent; the implementation independently requires exact split totals. Do not infer percentage-based splits from older third-party descriptions.

## Unresolved provider questions / activation blockers

1. Confirm the employer-owned merchant/service-type onboarding model and whether BusinessPaddi may generate employer payroll instructions without collecting funds into its own account. This POC has one operator-configured UAT merchant only; it is NOT a production multi-merchant credential model.
2. Obtain written confirmation that salary recipients can be approved split beneficiaries, how account profiling/linkage works, and which sandbox account fixtures are authorised. A bank dropdown entry is not Remita verification. No profiling or name-resolution route is invented here.
3. Confirm limits on beneficiary count, invoice amount, permitted payroll use, payout timing, fees, deductions, tax treatment and rejected/reversed recipients. Exactly one fee bearer is documented; this adapter assigns that flag to the separately approved BusinessPaddi vendor fee, never salary. The fee is the gross vendor allocation; any provider fee may reduce that allocation. Provider fee is UNKNOWN, not zero, until Remita supplies a quote/contract.
4. Confirm the account-holder verification API/product appropriate to this merchant. Other verification/transfer products in the documentation have different authentication; they do not establish split-invoice entitlement. BusinessPaddi's bank catalogue remains a maintained snapshot, not provider eligibility evidence.
5. Obtain a supported recipient-settlement/reversal feed and its signature/authentication contract. RRR collection status exposes no verified per-salary settlement in the researched contract. Sandbox therefore always reports recipient settlement UNKNOWN, even after a paid RRR.
6. Confirm notification authentication, retry policy, source restrictions, event IDs and cancellation semantics. Unsigned signals only request an authenticated status lookup. No public mock-simulation endpoint is exposed.
7. Confirm a supported payment-instruction URL. The researched invoice response gives an RRR, not a payment link. The application returns no invented payment URL.
8. The documentation requires UAT/KYC and go-live approval for first-generation services. Request employer-specific sandbox credentials and approved fixtures directly from Remita. We do not copy public example keys. Sandbox calls remain blocked until credentials, beneficiary approval and an explicit sandbox entitlement flag are supplied. Local code cannot determine whether an arbitrary secret is a production secret: the operator must attest sandbox provenance; production hosts/mode are rejected mechanically.

## Repository plan and reuse

Existing PayrollBatch/PayrollRecipient already implement draft creation, calculation, tenant-scoped relationships, encryption and independent approval. Keep their endpoints and immutability guards. Add PayrollPayment as the instruction/fee approval envelope, with an encrypted immutable beneficiary snapshot and integer-kobo totals; do not create another PayrollRun/PayrollItem store. Link line IDs to existing recipient IDs, with a separate PLATFORM_FEE line. No employee status/eligibility is updated.

Permissions are existing catalogue grants: prepare requires payments:view + payments:create; instruction approval requires payments:view + payments:approve and an independent actor; invoice generation requires payments:view + invoices:create; status reads require payments:view + invoices:view; cancellation requires payments:view + payments:cancel. Draft payroll preparation and approval continue through the existing payroll endpoints.

Approved salary snapshots cannot be edited. Payment-instruction cancellation does not cancel an approved payroll batch or release its obligation constraints. Changing salaries for the same period requires a separately designed approved-batch revision/obligation-release workflow; that capability stays blocked rather than bypassing existing guards. A cancelled instruction can be replaced for the SAME unchanged batch through fresh instruction approval.

See [local setup and API examples](remita-local.md) and [OpenAPI](remita.openapi.json). Live mode, transfers, wallets, escrow, balances, funding instructions and payroll custody are deliberately absent.

Merchant/service identity is frozen as a binding hash in the approval snapshot. Changing the configured merchant, service type or sandbox host blocks invoice creation for the old instruction; create a fresh instruction and obtain approval instead. API-key rotation for the same merchant is not part of that hash. A callback matching an unresolved order may request order-status reconciliation, but its RRR is never accepted as verified evidence. Accepted signals are audited atomically with their queue request.
